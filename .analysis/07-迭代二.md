## 2. P1-6：加密槽失败分类（出厂默认提示词的"体检单"）

### 2.1 旧行为的洞

`openSlot()`（原 `table-read.js:6-18`）任何失败都 `return ""`。槽打不开时：
- `defaultOverrideText()` 返回空 → 出厂默认提示词无声消失；
- 用户看到的不是报错，而是"提示词怎么空了/变回原样了"；
- 谁也说不清是槽没打进去、密钥不匹配、还是载荷被改坏。

### 2.2 改动

`openSlotDetailed(parts)`（`table-read.js:21-52`）分三段 try，失败各归其类：

| reason | 含义 | 对应动作 |
|---|---|---|
| `decrypt` | AES-GCM 认证失败：密钥/IV/TAG 不符或槽内容被改（GCM 认证标签就是干这个的） | 查 `slot-status.json` 里的 error，对版本/文件 |
| `decompress` | 解密成功但 inflate 炸：载荷截断/损坏 | 对 `asset-table.js` 的 SLOT 完整性 |
| `empty` | 全解开但内容空白：embed 环节封了空正文 | 重跑 `npm run embed-prompt` |

- `core.js:7707 slotStatus()`：进程内只解一次，失败写 `$DSH_HOME/dsh-purge/slot-status.json`；
- `core.js:7729 defaultOverrideText()`：**对外行为不变**（失败仍返回 ""），只是不再无声；
- `gatherState()` 暴露 `slot`（`core.js:8115`），`purge_status` 首屏渲染（`index.js:144-146`）。

## 3. P2-12③：report-replay 回归网（18 例，第一轮抓到真 bug）

新增 `scripts/test-report-replay.mjs`，覆盖四组纯函数：

| 函数 | 用例数 | 钉住的边界 |
|---|---|---|
| `parseTarget` | 7 | IPv6 方括号（**历史事故现场**：`http://[2001:db8::1]:8080/x` 不得解析成 `2001:db8:`）、默认端口、无协议、空串 |
| `parseCurl` | 3 | 方法/数据/头/cookie/开关、非 curl→null（不猜） |
| `buildHttpRequest` | 4 | **Host 头必须在报文里（真 bug 锁）**、JSON 体自动 Content-Type + 多字节 Content-Length、头去重、无 URL→null |
| `buildCurlCommand` / `fillTemplate` | 4 | 真实 curl 原样保留、IPv6 + 单引号转义、占位符如实报告剩余 |

### 3.1 抓到的真 bug

```js
// report-replay.js（修前）
const lines = [method + ' ' + path + ' HTTP/1.1', 'Host: ' + hostHeader]
...
return [lines[0], ...headers, '', body].join('\r\n')   // ← lines[1]（Host）被丢弃
```

**后果**：报告里每一条合成报文都没有 Host 头（HTTP/1.1 必带），粘进 Repeater 直接是非法报文。修后（`:137`）：

```js
return [...lines, ...headers, '', body].join('\r\n')
```

> 这正是 `00-总览.md` §11 P2-12 想要的东西：`report-replay.js:16-26` 记过一次 IPv6 事故，靠注释记忆；现在靠 18 条断言记忆。

## 5. P1-7：更新包哈希（供应链的"落地前"一环）

### 5.1 改动

`overlayFromZip`（`update.js:920-928`）现在的顺序：

```
下载 → createHash("sha256") → assertExpectedSha() → recordDownload() → 落盘 → 解压 → 覆盖
```

| 件 | 位置 | 说明 |
|---|---|---|
| `assertExpectedSha(sha256, url)` | `update.js:104` | 设了 `DSH_PURGE_EXPECT_SHA` 就强校验：非 64 位十六进制报错、哈希不符**直接抛错**（不解压、不覆盖），错误信息里带期望/实际值和指路 SHA256SUMS.txt |
| `recordDownload(info)` | `update.js:92` | `{ref, url, sha256, bytes, at}` 原子写 `last-download.json` —— "当时装进来的到底是什么"有据可查 |
| SHA256SUMS.txt | `release.yml:61-63` | Release 产物自带哈希清单，供 `DSH_PURGE_EXPECT_SHA` 取值 |

### 5.2 边界（如实声明）

- 这覆盖的是**插件自更新通道**（release zip / git ref）。宿主 plugin-manager 走 codeload tarball 的那一路（本机 1.1.73 就是这么进来的）在宿主侧，插件拦不到 —— 但 `installed-rev` / `applied.json` 已记录落地的 rev，配合 `last-download.json` 至少自更新方向全程可对账。
- 校验是**显式 opt-in**（设环境变量才钉死）：默认不设阈值，避免上游改打包方式时把所有人的更新都钉死。想长期钉死的用户在 AGENTS.md/env 里配一条即可。

## 9. 插曲：自动更新冲掉手术 → 钉版本（v1.1.78）

### 9.1 发生了什么

用户重启 dsh 后，插件从 1.1.73 **自动升级到上游 1.1.78**（`auto-update-guard.json`：`2026-10-24T17:18:53Z`，上游 `671011a7`），整个 `lib/` 被覆盖——P0/P1 两轮手术全部冲掉。

事后取证还原了链条：

- 覆盖发生在**重启瞬间还跑着的 1.1.73 代码**里（它那一版仍有启动自动升）；**1.1.78 已把它关掉**——其 `autoUpdateIfNeeded()`（update.js:1128-1136）明确写着 `skipped: "manual-only"`、注释"启动路径永不自动升"；
- 同时上游在 1.1.74-78 里**自己修了** additionalProperties 问题（tools.js 9 处 object 全部显式），64 工具注册正常——所以"工具消失"这个原始故障在上游侧已闭环；
- 但 **Host 头 bug 仍在**（report-replay.js:135），槽/apply 报告/更新哈希三项可观测性上游仍然没有。

### 9.2 钉版本（方案 B，双保险 + 机制内做法）

| 保险 | 改动 | 依据 |
|---|---|---|
| 依赖钉死 | `~/.dsh/profiles/web/package.json` 的 `dsh-purge` 依赖从 `codeload…/refs/heads/master` 改为 `refs/tags/v1.1.78` tarball（备份 `package.json.pre-pin.bak`） | 这正是上游 `pinInstalledSpec()`（update.js:308-332）自己升级时干的事——**机制内形态**；锁文件由 pnpm 重新解析一次性写一致（注释里明确警告手改锁文件会毁掉 profile，#118 教训） |
| 频道钉死 | `~/.dsh/dsh-purge/channel.json` 写 `"pin": "v1.1.78"`（备份 `.pre-pin.bak`） | 面板/更新器按 pin 显示"已钉住"而非"有新版本"（update.js:650-651） |

pnpm 重解析实测：锁文件三处全部指向 `refs/tags/v1.1.78`，装出 **1.1.78**。`[ERR_PNPM_IGNORED_BUILDS]` 跳过了插件的 `postinstall`（`ensure-profile-bundle.mjs`）——核验后无影响：profile 的 `dsh.profile.bundles` 本来就含 `dsh-purge`，该脚本要补的正是这一笔。
